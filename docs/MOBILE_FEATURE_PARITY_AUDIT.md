## 1. Executive Summary & Audit Methodology

This audit evaluates the feature parity, security controls, and source-of-truth adherence of the **ChaseHorse-EMS Mobile Application** (`apps/mobile`) in comparison with the **ChaseHorse Web Application** (`src/`) and the official **ChaseHorse ERP Implementation Blueprint**.

### Scope of Audit
1. **Blueprint Specifications:** Sections 1–16 of the official blueprint covering identity, field tasks, dynamic checklists, AI-assisted evidence verification, Operations Manager review queues, append-only wallet ledger, fleet transport management (TMS), and audit logs.
2. **Web Application Implementation:** Every route, page (`src/pages/*`), UI component, API client (`src/api/restApi.ts`), and access control hook (`src/config/access.ts`, `src/context/*`).
3. **Mobile Application Implementation:** Every screen (`apps/mobile/src/screens/*`), navigation flow (`apps/mobile/App.tsx`), component (`apps/mobile/src/components/*`), and mobile API client (`apps/mobile/src/api/restApi.ts`).
4. **Backend REST APIs:** All Spring Boot controllers, services, queries, DTOs, security configurations (`backend/erp-api/src/main/java/com/chasehorse/*`), and database schema migrations (`V1__initial_schema.sql`, `V2__enable_rls.sql`).
5. **Security & Data Integrity:** Verification of server-enforced JWT identity, role-permission matrices, tenant/customer isolation, atomic concurrency protection, absence of fake/synthetic client fallbacks, and storage security.

## 3. Discovered Security & Integrity Vulnerabilities

### High & Medium Findings Identified During Audit

1. **SEC-01 (High): Missing Admin/Operations Role Flow on Mobile (`apps/mobile/App.tsx`)**
   - *Impact:* An `ADMIN` or `OPERATIONS` user logging into the mobile app was greeted with a blank screen (`return null;`). They had no mobile interface to review evidence, manage worker accounts, or inspect operational metrics.
   - *Fix:* Introduce dedicated role navigation for `ADMIN` with tabs for System Overview, Account Approvals, Evidence Review, and Employee Directory.

2. **SEC-02 (High): Hardcoded Client Fallbacks & Synthetic Identity in Customer Screens**
   - *Impact:* `CustomerDashboardScreen.tsx` hardcoded `customerId: 'cust-apex'`, fake statistics `tasks.length || 24`, and fake contact name "Rahul Kumar". `CreateTaskScreen.tsx` hardcoded `customerId: 'cust-apex'` and static GPS `16.2418, 80.6448`.
   - *Fix:* Purge all fake fallbacks. Use authenticated `user.id` or let backend derive customer ownership from JWT; pull real stats from `/api/v1/dashboard/stats`.

3. **SEC-03 (High): Local-Only Simulated Transport Booking (`CustomerTransportScreen.tsx`)**
   - *Impact:* Booking a freight truck only displayed a local `Alert.alert` with a client-generated `CH-TRK-XXXX` string without dispatching an API call to `/api/v1/tms/shipments`.
   - *Fix:* Wire `handleBook` directly to `mobileApi.createShipment` which issues `POST /api/v1/tms/shipments` and persists in `tms_bookings`.

4. **SEC-04 (Medium): Fabricated AI Verification Scores in Camera HUD & Manager Review**
   - *Impact:* `CameraHUD.tsx` used `setTimeout` to generate a fake "96.8% Confidence" pass. `ManagerReviewScreen.tsx` rendered static text asserting AI pass.
   - *Fix:* Remove fake AI score generators. Mark newly captured evidence as `"PENDING REVIEW"`; in `ManagerReviewScreen.tsx`, display real verification data from backend or explicit "Pending Operations Review".

5. **SEC-05 (Medium): Client-Calculated Wallet Balance (`WalletScreen.tsx`)**
   - *Impact:* `WalletScreen.tsx` computed the worker's balance using `txns.reduce(...)` on the client, violating the ERP blueprint requirement that the backend ledger must be the sole authority.
   - *Fix:* Add `GET /api/v1/wallets/{id}` endpoint returning server-calculated `balanceInr` and `pendingInr`; update mobile wallet to display backend-authoritative balance.

6. **SEC-06 (Medium): Static Hardcoded Checklist Fallback (`ActiveTaskScreen.tsx`)**
   - *Impact:* If task checklist was empty, `ActiveTaskScreen.tsx` defaulted to a 3-item array with 2 items pre-checked as completed.
   - *Fix:* Fetch dynamic checklist templates from `/api/v1/checklist-templates/{id}`; initialize all items as uncompleted; prevent submission until all required items are verified.

7. **SEC-07 (Low): Missing Server-Side Profile Update Endpoint**
   - *Impact:* Customers and field workers could not update their mobile phone or operating cluster via the API.
   - *Fix:* Add `PUT /api/v1/profiles/me` endpoint in backend and connect mobile profile screens.

## 4. Implementation Plan & Execution Order

To achieve 100% production-oriented parity, the following phases are executed in dependency order:

1. **Step 1 — Database & Backend API Enhancements:**
   - Add Flyway migration `V3__seed_checklists.sql` to populate standard checklist templates.
   - Add `GET /api/v1/wallets/{employeeId}` in `WalletController.java` for authoritative balances.
   - Add `PUT /api/v1/profiles/me` in `ProfileController.java` for profile updates.
   - Add `POST /api/v1/tms/shipments` price validation in `TmsController.java`.
   - Update `EvidenceController.java` to return real/pending AI verification statuses.
   - Allow `MANAGER` role in `ApprovalController.decideApproval`.

2. **Step 2 — Mobile API Client Hardening (`apps/mobile/src/api/restApi.ts`):**
   - Add `getDashboardStats`, `getWalletAccount`, `getChecklistTemplate`, `listChecklistTemplates`, `createShipment`, `listEmployees`, `updateProfile`, `listNotifications`, `markNotificationRead`.

3. **Step 3 — Mobile UI & Workflow Parity Implementation:**
   - Update `CustomerDashboardScreen.tsx`: Real backend stats, no fallback numbers.
   - Update `CreateTaskScreen.tsx`: Dynamic checklist templates, real customer identity, real GPS extraction.
   - Update `CustomerTransportScreen.tsx`: Real server booking via `POST /api/v1/tms/shipments`.
   - Update `CustomerProfileScreen.tsx`: Real profile editing, real emergency support hotline.
   - Update `ActiveTaskScreen.tsx`: Dynamic checklist loading, no pre-checked items.
   - Update `CameraHUD.tsx`: Real metadata capture, explicit pending verification state.
   - Update `ManagerReviewScreen.tsx`: Real evidence list, real rework modal with notes.
   - Create `AdminDashboardScreen.tsx` and `EmployeeDirectoryScreen.tsx` for Admin role.
   - Update `apps/mobile/App.tsx`: Full RBAC navigation for `admin`, `manager`, `employee`, and `customer`.

4. **Step 4 — Automated Testing & Verification:**

   - Execute `mvn test`, web `typecheck` / `build`, and mobile `typecheck`.
